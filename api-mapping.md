# API Mapping

## Objective

The objective of the API mapping phase was to identify and document the application's API communication, endpoints, parameters, authentication mechanisms, and data resources.

The mapping was performed after reconnaissance and was based on observing normal application traffic through the browser's Developer Tools.

## Scope

API mapping was limited to the assets and functionality defined in `scope.md`.

Testing focused on API communication generated by the application during normal authenticated use.

## Methodology

API communication was observed through the browser's Network panel while using the application normally.

The assessment focused on:

- Identifying API endpoints
- Identifying API resources and tables
- Observing request methods and parameters
- Identifying authentication mechanisms
- Reviewing authorization-related parameters
- Identifying sensitive data returned by API responses
- Determining whether the application communicated directly with Supabase
- Identifying areas requiring further authorization testing

## Tools

The following tools were used:

- Browser Developer Tools
- Network panel
- HTTP request inspection
- Browser Application/Storage inspection
- Supabase REST API observation

## Application Architecture

The assessment showed that the frontend communicates directly with Supabase for most data operations.

No separate application backend was observed between the frontend and the Supabase REST API for these operations.

This means that access control for database resources depends heavily on Supabase Row Level Security (RLS).

The architecture can therefore be broadly represented as:

```text
User Browser
     |
     | HTTPS / API requests
     v
Kriva Frontend
     |
     | Supabase REST API
     v
Supabase
     |
     +-- Database tables
     +-- Authentication
     +-- Row Level Security (RLS)
